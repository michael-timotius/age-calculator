community-settings-ops-manage-settings

Read Setting Workflow

  • Given no settings have been saved for the community, when the page loads, all fields appear blank
  • Given settings exist, when the page loads, each field shows its saved value
  • Given the API is unreachable, when the page loads, fields appear blank and no error toast is shown

Update Setting Workflow

  • Given a Community Admin, when submitting a valid key and non-blank value, the setting is saved and a success toast is shown
  • Given a Community Admin, when submitting a blank value, the request is rejected with "Value must not be blank"
  • Given a Community Admin, when submitting an unknown key, the request is rejected with "Invalid setting key"
  • Given a Community Member (non-admin), when attempting an update, the request is rejected with an authorization error and the UI reverts to the previous value

notification-system

notification-system-ops-list-notifications

  • Given a member with no notifications, when they load the notification list, they receive an empty list with no errors
  • Given a member with 5 notifications in community A and 3 in community B, when they load the list for community A, they see exactly 5 notifications
  • Given a member with 25 notifications, when they load the first page (default 20 per page), they receive 20 notifications and a cursor for the next page
  • Given a member attempting to access another member's notifications, the request is rejected with an access denied error
  • Given an invalid pagination cursor, when the member loads the list, the response treats it as the first page

notification-system-ops-mark-read

  • Given an unread notification, when the recipient marks it as read, the notification returns as read and the unread count decrements by 1
  • Given an already-read notification, when the recipient marks it as read again, the request succeeds with no state change (idempotent)
  • Given a notification belonging to member A, when member B attempts to mark it as read, the request is rejected with access denied
  • Given a notification from community A, when the request is scoped to community B, the notification is not found

progression-system

progression-system-ops-activation

  • Given a valid template, when admin activates for community with type "level" → 1 config, 50 stages, community progression active
  • Given community already has active progression → activation rejected
  • Given community has active progression with user checkpoints, when deactivated → deactivation timestamp set, checkpoints preserved unchanged
  • Given template switch → deactivate old, activate new; user checkpoints preserved from prior era

progression-system-ops-exp-progression

  • Given user at Level Stage 2 with 120 EXP (target = 200), when admin grants 100 → experience = 220, crosses threshold → advance to Stage 3 with carry-over 20, one log created
  • Given admin tries to grant Level EXP but is not admin → request rejected (forbidden)
  • Given community has no active Tier progression, when redeem approved → no EXP granted, no error

progression-system-ops-seasonal-reset

  • Given Tier user at Stage 3 with 500 EXP, when seasonal reset runs → retained = 250, stage = 2, log created
  • Given Tier user at Stage 1 with 300 EXP, when seasonal reset runs → retained = 150, stage stays 1, log created
  • Given community with tier_reset_enabled = false → community entirely skipped, no changes
  • Given Level checkpoint → never affected by seasonal reset

progression-system-ops-stage-listing

  • Given "level" type has 50 stages → 50 stages returned in ascending ordinal order, no community filtering
  • Given stage at ordinal 3 has 2 privileges for community X → 2 privileges returned with cast values
  • Given stage at ordinal 1 has no privileges for community X → empty list returned (not an error)
  • Given invalid progression type → rejected (not found)

progression-system-ops-checkpoint-read

  • Given user at Level Stage 3 with 120 EXP → response includes ordinal 3, exp 120, target EXP, privileges for stage 3 in that community
  • Given user has no checkpoint → null/empty returned, not an error
  • Given user has both Level and Tier checkpoints → two separate reads, never merged
  • Given 3 EXP log entries → 3 entries returned in descending timestamp order
  • Given non-admin requests community list → rejected (forbidden)

progression-system-ops-level-system-permissions

  • Given community has vip_access_enabled = false, when admin updates to true → value updated, no other records changed
  • Given actor is not admin → rejected (forbidden)
  • Given community + key does not exist → rejected (not found), no new record created
  • Given active progression, when admin updates tier_reset_enabled = false → flag updated, no deactivation required, seasonal reset job will skip this community

progression-system-ops-vip-access

  • Given user at Level ordinal 50 and vip_access_enabled = true → access granted
  • Given user at Level ordinal 49 and vip_access_enabled = true → access denied
  • Given user at Level ordinal 50 and vip_access_enabled = false → access denied
  • Given user has no Level checkpoint and vip_access_enabled = true → access denied

progression-system-ops-template-management

  • Given 5 stages with max stages count = 5, sequential ordinals, increasing target EXP → template created
  • Given max stages count = 3 but 5 stages provided → rejected
  • Given ordinals [1, 2, 4] (gap at 3) → rejected
  • Given stage 3 target EXP < stage 2 target EXP → rejected
  • Given admin updates name only → name changed, stage structure unchanged
